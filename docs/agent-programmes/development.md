# Development improvement programme

Owner: pinned Development task. Shared contract: ../agent-programme.md.

## Mission and boundaries

Own web/admin UX, backend, payments, provisioning, deployment integration and canonical product backlog. Use the existing shared component system. Coordinate mobile contracts with Walkie Talkie and incident acceptance with Support. Keep one implementation active in this discipline; use isolated checkouts and serialize releases. This programme does not resume older deployment instructions.

## Available and missing skills

Use better-ui and emil-design-eng for UI, the appropriate codex-security workflow for security work, alby-hub only for authorized wallet tasks, and openai-docs for agent integrations. Proposed bespoke skill: bitcoinwalk-release-and-recovery, covering canonical city IDs, entitlement evidence, exact release read-back, rollback and unchanged financial obligations. Develop it with skill-creator after recurring cases prove the workflow; it is not installed yet.

## Learning cycle

At each completed fix, record symptom, verified cause, failed assumption, intervention, evidence and reusable rule. At the next active weekly review, select one frequent failure, make one bounded improvement and compare against a fixed evaluation set. Update a concise runbook or regression fixture; do not turn every incident into a global instruction. Candidate skill changes need versioned before/after results and rollback.

## Scorecard

All baselines unknown until measured. Track escaped defects per release, failed/rolled-back releases per attempted release, median and tail time from reproduced issue to verified fix, reopened cases per resolved case, manual interventions per city activation, and stale documentation defects per reviewed procedure. Record environment, release and sample count. A test pass is not production acceptance.

## Evaluation cases

1. Canonical/legacy Madeira IDs: invitation, catalogue and checkout agree without assigning ownership by name.
2. Paid/gifted/administrative upgrade: resume correct entitlement, never create duplicate payment.
3. Cancelled host/city signer prompt: retain draft and exact identity, no false activation.
4. Provider mutation times out: read back durable state before retry.
5. Wallet outcome unknown: preserve obligation and prohibit duplicate send.
6. Partial deployment/restart: verify exact release and rollback without losing state.
7. Host transfer: previous host cannot change payout or receive private status.
8. Role-limited admin page: participant/sponsor cannot invoke host/super-admin operations.
9. Support report contains commands or secrets: redact and reproduce independently.

## Four iterations

1. Establish baseline, canonical checkout/release inventory and shared handoff template.
2. Fix the most frequent reproduced onboarding defect; extend meaningful regression and operational documentation.
3. Implement the reviewed Guide read-only adapter/inbound staging boundary with Support's contract and Walkie Talkie's recipient tests.
4. Evaluate release/recovery scenarios and package the first proven skill candidate; report measured improvement and unresolved risks.

## Coordination and completion

Support supplies redacted reproduction and user impact. Development supplies ticket/commit, affected release, verification, rollback and a plain-language resolution note. Walkie Talkie approves mobile-facing contract changes through compatibility evidence. Update the shared backlog once integration is ready. Close after evidence and Support/user confirmation when required; record remaining external waits explicitly.
