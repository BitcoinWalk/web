## Current iteration backlog

### BW-79 implementation plan — registration handoff and shared account connection

Status: 🟠 In progress. App 0.3.115 implements the first four stages for staging acceptance. It shares the registration account module with dashboard entry, preserves the selected signer through client navigation, redirects Basic after relay acknowledgement and Pro after verified settlement, and derives creator-visible submission state from signed relay records. Pro automatic approval remains future BW-78 scope.

**Intended journey.** After Basic submission is acknowledged, navigate to `/admin` with the connected identity and show the submitted city as Awaiting approval. After Pro submission and server-verified payment, navigate to the same dashboard. Until BW-78 is implemented, show Payment received — awaiting approval; afterwards show Activation pending until signed approval and relay read-back establish that the city is live. Payment alone must never produce an Approved badge. Keep payment, approval and infrastructure-provisioning statuses separate. An approved city does not imply its dedicated relay, identity or Lightning address is ready.

**Stage 1 — reusable account module and session ownership.** Extract the Step 2 account UI into a shared component with configurable headings for registration and dashboard entry. Support Create new account, Connect with browser extension, private-key text/file import, and bunker text/QR connection using the existing desktop/mobile guidance and copy. Move signer ownership from the route component to a client session provider shared across `/start` and `/admin`. Use explicit extension/local/remote adapters, keeping the chosen identity stable when an extension has another account selected. Current component cleanup restores `window.nostr` and closes bunker sessions on unmount; replace that route-bound lifecycle so client navigation preserves the chosen session. Disconnect/account switching must close remote subscriptions, discard local secret references, invalidate pending work and clear identity-specific dashboard data. Store no nsec, bunker secret or session credential in URLs, browser persistent storage, analytics or server state. A hard refresh may require reconnection; state that clearly and retain the private-key backup flow for new accounts. Audit dashboard signing and encryption operations and request remote-signer capabilities as needed; registration's current permission list is not sufficient evidence of dashboard compatibility.

**Stage 2 — dashboard entry.** Replace the disconnected Connect signer entry with the shared account module in the main dashboard area; use a dashboard heading without Step 2 numbering. Prefer Connect with browser extension for returning desktop users and remote signer guidance on mobile; keep Create new account available but avoid implying an existing organizer needs another account. When arriving with an active registration session, load the dashboard automatically without a second login or signature just to navigate. Show the existing compact identity and Disconnect controls once connected. New accounts entering `/admin` directly see a useful empty state with Start a city. Existing deep links resume their intended screen after connection, subject to current permissions.

**Stage 3 — pending-city visibility.** Add an owner-scoped submissions summary to the dashboard overview, available even when the identity has no approved city grant and is currently classified as a member. Resolve ownership and status from signed records; never trust a city ID or success flag in the redirect. Show city name, Basic/Pro tier, Awaiting approval/Approved/Needs changes state, verified payment status where relevant, and the relevant next action or public link. Distinguish a submitted initial walk from a published walk. Preserve editor/host/super-admin boundaries: being able to see one's pending request grants no city editing or walk publication permissions. Use shared reads and bounded refreshes to avoid recreating the dashboard relay-rate-limit issue. Clear stale data on identity changes; unavailable reads must not appear as missing submissions or zero cities.

**Stage 4 — registration completion and recovery.** Use client navigation to `/admin` after Basic relay acknowledgement and after Pro server-confirmed settlement. Pass only non-secret correlation identifiers for highlighting the submitted city; authoritative dashboard reads determine status. Pro's pre-invoice signed submission must not trigger the Basic completion redirect. Prevent repeated settlement callbacks or double clicks from creating duplicate submissions, invoices or navigation. If visibility read-back lags, show Submitted — confirming status and retry with bounded backoff. Relay/payment uncertainty remains a recoverable pending state; do not invite duplicate city creation or repeat payment. Closing the payment page must remain recoverable through the owner's dashboard payment/submission record. Payment reconciliation continues independently of the browser. Show a concise arrival confirmation and focus the new city card or status heading accessibly.

**Stage 5 — optional BW-78 integration.** Consume BW-78's verified signed approval result when that future policy is enabled. Pro creators see Activation pending, Approved, or Needs review depending on the actual decision. Basic cities retain review; Pro conflicts and moderation exceptions remain visible with a useful explanation. Do not implement the automation signer or approval policy as part of BW-79, and do not delay the common account/dashboard handoff on it.

**Stage 6 — acceptance and rollout.** Test Basic and Pro completion with extension, generated/imported local key and bunker/QR sessions; same-identity navigation without reconnect; direct `/admin` login and empty state; a creator with only a pending request; account switching with an older extension identity; private-key backup and hard-refresh reconnection; remote rejection/disconnection and capabilities; late/duplicate settlement, relay outage and restart recovery; no duplicate invoice/submission; unauthorized record/action isolation; desktop/mobile keyboard and focus behaviour. Verify city states before and after manual approval, and later BW-78 approval/exception outcomes. Deploy to staging and obtain real signer/mobile acceptance before completion. Release notes and backlog must distinguish the delivered handoff from the deferred Pro approval automation.
