Dependency increment: `replication_bundle.go` exports a bounded (256 KiB) snapshot only for an already stored, currently public ordinary occurrence or the exact initial proposal released by the current approval. It includes the signed creator provenance, current grant, approved revision, approval, and any initial walk explicitly released by that approval. Historical backfill does not reapply the new-publication time horizon, but still requires the current approval/editor authority, schema, signature and retained-tombstone checks. Receiver validation checks signatures, scope and the dependency graph in a disposable unserved database. Tests cover missing/corrupt/duplicate records, wrong city/version/target, authentication, canceled source events, retained past occurrences, first-walk delivery-worker refresh and revoked-city restart reconciliation. This internal provenance must not become a publicly exposed proposal feed.

Source-ordering increment: `replication_journal.go` adds an opt-in durable bbolt acceptance journal and strict operator-owned paid-city destination registry. The journal is written inside the relay's locked durable-write path after event storage, deduplicates signed event IDs, persists a monotonic per-city head, and records configured-city grants, decisions, ordinary occurrences, blocked initial proposals and cancellations. Drafts, chat and unconfigured cities remain excluded. A blocked initial proposal becomes eligible only when the exact approval releases it; the updated eligibility and policy IDs are persisted before delivery refresh. Local freshness checkpoints require an eligible accepted target, its unchanged configured destination, current public visibility, current city approval and current grant. Cancellation and city revocation invalidate the checkpoint. Before the relay serves traffic, bounded startup reconciliation scans the authoritative event store, restores any record missed in the separate-database crash gap, tolerates historical approvals when the current city state is revoked, orders recovered tombstones after occurrences, and must complete before checkpoints are available. Recovery is deterministic and idempotent. A registry fingerprint prevents implicit endpoint migration; adding one city requires the explicit additive migration mode and cannot redirect or remove an existing city.

Source-outbox increment: `replication_outbox.go` integrates a bounded durable Go outbox into the journal transaction. Eligible rows contain the exact organizer-signed event, validated dependency bundle, current source checkpoint and immutable operator-configured destination. Delivery refreshes source eligibility, requires an exact event/checkpoint acknowledgement, uses bounded exponential retry state and retains sanitized status codes only. Pending canceled/revoked work is suppressed; already acknowledged work becomes `cancellation-required` or `revocation-required`. Startup reconciliation repairs missing outbox rows as well as journal gaps. Tests use an injected fake transport; the previous TypeScript outbox remains only a prototype and is not the replication authority.

Receiver increment: `replication_receiver.go` validates the authenticated service, immutable city/destination scope, exact envelope occurrence, dependency graph and approval/grant IDs before changing receiver state. The exact envelope and monotonic per-city head are committed together in the destination Bolt database. Dependencies install before the occurrence; the occurrence is the last public write and no exact acknowledgement is returned until it is readable. Interrupted work remains `staged`, blocks later checkpoints and resumes idempotently from the same envelope. Retained destination tombstones, newer revocations, conflicting replays, stale checkpoints and implicit receiver-scope changes fail closed. Tests inject a target-write failure and verify no partial occurrence visibility, exact retry recovery and destination suppression.

Ordered-removal increment: the source forwards exact signed kind-5 organizer tombstones and admin-signed city revocations using the same monotonic envelope and exact-ack protocol. A cancellation is sent only for an occurrence that reached or was concurrently reaching the destination. A city revocation is standalone when acknowledged destination state exists; an in-flight occurrence retains the revocation control and cannot overwrite it with a stale success. The receiver validates target/author or admin authority, installs the retained control record, verifies the event is no longer publicly readable and then acknowledges. Revocation supersedes cancellation, and no relay history is physically erased.

Transport increment: `replication_transport.go` carries a service-signed kind-6000 wrapper over the exact operator-owned root `wss://` endpoint and requires NIP-42 authentication by the same dedicated identity. It applies five-second connection/delivery deadlines, a 400 KiB envelope limit and 512 KiB WebSocket ceiling. The wrapper is intercepted after receiver success and deliberately returns Khatru's duplicate result so it is acknowledged but never stored, broadcast or exposed as a public event. Source activation requires an owner-only key file; receiver activation requires exact city, service-pubkey and destination settings. Tests exercise real local WebSockets for occurrences, cancellations and revocations, reject another authenticated key, and verify wrappers never enter storage.

TLS rehearsal increment: `TestReplicaTransportTLSSeparateRelays` creates isolated source and destination relay instances with different Bolt stores and a real TLS WebSocket listener. It proves the default client rejects an untrusted certificate, then uses the rehearsal CA to exercise the production source journal/outbox, strict proxy-derived WSS identity, NIP-42, receiver acknowledgement, exact signed-event equality, non-persistence of the private wrapper and ordered cancellation. ## Fixed scope

All website URLs stay at `bitcoinwalk.org/<city>` and `/<city>/<nevent>`. Paid city subdomains identify relays, not separate websites. Public signed occurrences should ultimately exist on both the shared event relay and the selected city relay, with identical event IDs and signatures. Private chat, DMs, keys and pending proposals must never enter the public replication pipeline.

6. **Implemented and signed-accepted:** super-admin Alerts expose pending/healthy/degraded state, reconciliation and sanitized per-city counts. Shared-relay acknowledgement remains required for the current official publication flow; city failure is a visible degraded state, not a reason to sign duplicate events.
7. **Two-city staging pilot accepted for implemented scope:** Memphis exact equality, receiver/source restart, receiver outage/retry, duplicate acknowledgement, private-wrapper exclusion, live create/edit/cancel and negative-policy probes pass. Nashville exact first-walk gating, approval delivery, revocation suppression, additive registry migration, cross-city isolation and post-revocation restart pass. 8. **Implemented in source, not live-accepted:** the `0.8.28` entitlement gate and two-phase planner/apply flow fail closed on wrong issuer, malformed evidence, inactive/superseded entitlement, implicit destination changes and time-of-check/time-of-use revocation. Full relay coverage is 82/82 with race detector and vet green. Remaining for BW-56: establish the staging-only authority and rehearse backup-first synthetic provisioning plus revocation. Real payment verification and production paid activation remain separate BW-17/BW-18/BW-23 gates.

The outbox, transport and receiver remain operator-controlled infrastructure, not a generic ingest service. Run one worker per queue. Destination changes do not silently redirect old deliveries. The replication secret belongs only on the source service; destinations receive only its public key. The Guide identity remains completely separate.

The Guide cannot publish through the receiver bypass, alter the paid-city registry, approve/revoke cities, inspect private chat through this pipeline, or autonomously perform destructive recovery. Any future AI capacity uses explicit tools with narrow permissions, auditable actions, opt-in organizer conversations and human escalation for policy, payment, moderation or infrastructure changes.
